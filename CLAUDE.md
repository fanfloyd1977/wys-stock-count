# WYS (Stock Counting App) — Claude Instructions

> All workspace rules (security, images, design, GitHub, environment) are defined in `../CLAUDE.md`. This file contains only project-specific notes.

## Project Overview
Stock counting app for a Thai lighting/smart-home integrator client, built together with a collaborator who works with the client directly. The client buys lighting/smart-home devices from vendors, resells and installs them for their own clients, and currently counts stock manually. Goal: replace that with an app, then sell it to the client once validated.

## Architecture (demo phase)
- **App:** single-file HTML/JS, hosted on GitHub Pages — iPhone camera scans vendor QR/barcodes (no physical scan gun available yet; a Zebra-style scan gun was suggested by the collaborator but is unconfirmed as an actual client requirement).
- **Backend/storage:** Google Sheets + Google Apps Script "web app," not Supabase — simpler for a demo, and the client already thinks in spreadsheet terms. Apps Script holds the Google credentials so nothing sensitive ships in the public GitHub Pages code.
- **Duplicate handling:** Apps Script checks if a scanned code already has a row — increments qty if yes, adds a new row if no. Needs `LockService` to avoid a race condition if two people scan the same code at the same instant.
- **Google account for this project:** `wys.trt@gmail.com` — dedicated account, separate from personal, to keep client data boundaries clean. Use an Incognito window (or a dedicated Chrome profile) when working in it to avoid Google Drive "unable to open the file" errors caused by multiple accounts mixing in one browser session.

## Open questions (unresolved)
- Does counting happen in a fixed warehouse or across install sites/technician vehicles?
- What system (if any) currently holds the client's stock numbers — spreadsheet vs real inventory software?
- Is a physical Zebra-style scan gun an actual client requirement, or just the collaborator's guess?
- **Unique key for counting:** vendor QR/barcode is likely just a SKU/product code (same on every unit of that product) — with SKU alone, the app can't tell "5 real units" from "same unit scanned 5 times by accident." Ask collaborator: when the client receives stock from a vendor/supplier, do they put their own unique identifier on each box/unit themselves (e.g. a running-number sticker)? If yes, that becomes the true per-unit dedup key instead of relying on SKU + physical "move as you scan" process.

- 2026-08-25: Reworked scan feedback after live testing surfaced two real UX gaps (user compared it to a physical scan-gun's press→beep rhythm):
  - **Timing mismatch fixed:** the scan-lock duration (used to be 1.2s) and the result-banner duration (used to be 2.6s) were different numbers — meaning the camera could accept a new scan while the previous result was still displayed, causing banner overlap/flicker. Both now share one constant, `SCAN_PAUSE_MS = 1400`. Camera is also now visually paused (`html5QrCode.pause(true)` + `.paused` dimming class) during that window via `resume()` after, instead of just silently ignoring input with no visual cue.
  - **Instant "read" beep added:** `playTick()` fires immediately on raw decode, before the network round-trip to Apps Script — closes the "did it actually scan?" gap a physical scanner doesn't have (it beeps optically, with no backend wait).
  - **"Already counted" alarm reframed:** repeat-scanning the same SKU during a normal count is the expected, successful case (not an error) — it now shows the same neutral green "Counted — code · now qty" as a first-time scan, no warning icon. The alarm styling (amber, `!` icon, buzz sound) is reserved for `FAST_REPEAT_MS = 3000` — the same code scanned again within 3 seconds, which is much more likely to be the camera re-reading the same physical box still in frame than a genuinely new unit.
  - Verified locally with Playwright + mocked Apps Script responses (new / normal-repeat / fast-repeat / rapid-double-call-ignored-by-lock) — all four cases behave as designed, no console errors.
- 2026-08-25: Adopted shared terminology for the scan cycle while debugging feel, in order: **Ready** (camera watching) → **Aim time** (user moves phone, human-controlled) → **Read** (camera decodes) → **Read beep** (instant, on Read) → **Sync** (background Sheet write) → **Result** (banner+sound) → **Pause window** → back to **Ready**.
- 2026-08-25: Chased the "3-5 sec before it counts" complaint through several rounds:
  - First assumed it was **Read** speed — narrowed `formatsToSupport` to QR-only (was testing 7 formats/frame) and dropped camera resolution to 640x480 via `videoConstraints` (had to move it there, not the `start()` first arg — that only accepts one key). Also widened the Pause window to 2500ms for real Aim time.
  - Turned out the real bottleneck was **Sync**, not Read — user clarified the delay was from the green "read" indicator to the "Counted" message appearing, i.e. after Read had already succeeded. Google Apps Script web apps are just inherently a few seconds slow (well-documented Google-side limitation, not something client config can fix) — and the old code had Result/Pause/camera-resume all waiting on that slow `fetch()` to resolve before doing anything.
  - **Fix:** decoupled the UI entirely from Sync. `onScanSuccess` now shows the Result banner, plays the sound, and schedules camera resume all locally/instantly (the fast-repeat check was already computed client-side, so no server round trip was ever needed for it). The actual Sheet write (`syncScan`) fires in the background and only surfaces a toast if it truly fails — exact live quantities are always available on the Summary tab instead of in the instant banner. Verified with Playwright using a mocked 4-second-delayed Apps Script response — banner appeared in ~0.5s, camera resumed at the fixed 2.5s mark regardless of the slow backend.
- **Next up:** live iPhone test of this decoupled version — confirm the rhythm actually feels instant now, and that Summary tab numbers still end up correct once background syncs catch up.
